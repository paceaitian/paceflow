我认为最有希望的主方向是：

> 从“强制 AI 走完整流程”，转向“分级门控的项目记忆与交付证据系统”。

### 1. 把产品拆成三个档位

- `memory`：只做上下文恢复、finding、correction、walkthrough，不阻断。
- `guarded`：只拦最关键的两件事——无计划写代码、无验证就结束。
- `strict`：保留完整 P-A-C-E-V-R，面向生产、高风险和合规项目。

大多数用户应该默认进入 `memory` 或 `guarded`，而不是 full strict。

### 2. 让真实证据替代流程标记

减少对 `APPROVED/VERIFIED/REVIEWED` 仪式的依赖，机械记录：

- 实际执行过的测试命令及退出码；
- Git diff、修改文件和提交；
- 审查发现与处置结果；
- CI、PR、部署结果。

Hook 不判断测试是否“足够”，但至少能区分“真的运行过测试”和“写了 VERIFIED”。

### 3. 大幅简化 Artifact 模型

建议只保留一个权威来源：

- `changes/<id>.md` 是权威；
- `task.md`、walkthrough、Obsidian 视图全部自动生成；
- 普通用户不需要理解 reservation、索引同步、9-key schema 和 writer lock。

复杂度应该由插件承担，不能暴露给用户和模型。

### 4. 把上下文恢复做成核心卖点

这是目前最可能产生长期留存的能力：

- 新 session 自动回答“上次做到哪”；
- 当前决策、未解决问题、验证结果自动恢复；
- compact 后恢复约束；
- finding/correction 根据当前文件和任务相关性注入。

宣传重点可以从“Hook 是法律”改成“项目不会因为换 session 而失忆”。

### 5. 建立 ROI 数据

本地记录且默认不上传：

- 拦截次数与用户覆盖次数；
- 误拦截率；
- 每个 CHG 的流程耗时；
- 恢复了多少跨 session 上下文；
- Review 真正发现了多少 P0/P1；
- 用户在哪一步 pause/disable。

没有这些数据，继续增加流程门只是在凭感觉优化。

### 6. 先稳定 Claude Code，不急着扩平台

短期优先：

- Windows/Linux/macOS CI 全绿；
- LTS/稳定版本，减少一天多个 patch；
- 一套真实业务项目案例；
- 外部贡献和安全策略；
- 把巨型 hook 模块继续拆小。

等核心模型稳定后，再考虑 Codex、Cursor 等适配层。

### 不建议继续走的方向

- 增加更多 frontmatter 字段；
- 增加更多强制 agent；
- 每种边界问题都新增一个 Hook；
- 把 PACEflow 做成通用任务管理器；
- 用更多自审文档证明自身价值。

一句话路线图：

> **先减门、保留记忆；再用真实执行证据强化关键门；最后才面向高风险团队提供完整 strict workflow。**
